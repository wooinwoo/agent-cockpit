## Design Specificity Verdict

**LLM assessment:** Cockpit feels authored for this product, not category-interchangeable. The terminal owns the visual field, while engraved labels, signal lights, session shortcuts, and a quiet matte control deck support the real work instead of turning it into a generic dashboard. The strongest product-specific interaction is the combination of live terminal focus, session-status rail, keyboard movement, and spatial grouping.

The weakness is not a lack of identity. It is that the current product surface must also carry the burden of explaining itself as a portfolio artifact. A first-time reviewer sees a capable operations bench but not the problem statement, design evolution, technical risks, or proof of impact.

**Deterministic scan:** The detector found 8 items in `index.html`: four font-size token deviations (`index.html:333`, `:1508`, `:1744`, `:1745`), two radius deviations (`:1741`, `:2026`), one raw color (`:2026`), and one flat-type-hierarchy warning (`:333`). The hierarchy warning is context-sensitive because the committed dense terminal system deliberately uses weight, spacing, and contrast. The `6px` overlay radius is also allowed in DESIGN.md prose despite missing from its frontmatter scale. The repeated font sizes and isolated `#fff`/`8px` remain genuine cleanup candidates.

**Visual overlays:** No reliable overlay is available. Mutable browser injection worked, but Impeccable's live server did not produce a usable connection record. A fresh 1440×900 local screenshot was used as the visual fallback.

## Overall Impression

This already looks like a real tool built by someone who felt the operational pain. The single largest opportunity is not another feature: it is a safe, curated way to demonstrate the tool and tell its engineering story without exposing the live workspace.

## What's Working

- **Terminal-first hierarchy is honest.** The active terminal dominates the frame while session status remains adjacent and non-modal. This directly matches the documented 99% terminal usage.
- **Power-user flow is unusually complete.** Numbered sessions, Alt navigation, scroll shortcuts, grouping, reordering, canvas pan/zoom, and visible shortcut help form a coherent operating model.
- **The visual language belongs to Cockpit.** Matte black surfaces, hairline divisions, small engraved mono labels, and restrained green/amber/red signals create a specific operations-bench character without ornamental dashboard cards.

## Cognitive Load

**Moderate: 3 of 8 checklist items fail.**

- Pass: single focus, semantic grouping, primary hierarchy, one task at a time, and working-memory support.
- Fail: chunking and minimal choices. A portfolio viewer simultaneously sees the left tool rail, six session tabs, six status rows, terminal controls, and the bottom utility deck. The live DOM contained 247 interactive elements across the full app.
- Fail: progressive disclosure for first-time viewers. Advanced controls are available, but the interface does not demonstrate the intended first three actions or explain why canvas/grouping matters.
- Decision points over four options include the left navigation rail, session strip/status list, utility toolbar, and three-terminal layout menu.

## Emotional Journey

The opening reaction is strong: it looks serious, fast, and operational. The valley arrives immediately afterward when a new viewer asks, “What problem am I looking at, and what should I try first?” The product peak is rapid keyboard switching and arranging multiple sessions while their state remains visible. The current ending is weak for a portfolio: README reaches a demo TODO, so there is no curated payoff, before/after story, or safe artifact to share.

## Priority Issues

### [P1] No safe showcase/demo state

- **Why it matters:** The live screen exposes real project names, work topics, branch/status information, and terminal content. That makes screenshots and recordings risky and prevents a repeatable demo.
- **Fix:** Add a one-click `Showcase mode` or `?demo=1` that loads deterministic fictional sessions, tasks, branches, and terminal output; masks machine paths and disables destructive/external actions. Include one polished 2-session and one 3-session grouping scenario.
- **Suggested command:** `$impeccable harden`

### [P1] The case study is missing and README truth has drifted

- **Why it matters:** `README.md` literally contains “데모 GIF / 스크린샷 추가 예정.” It also says 339 tests while the current suite has 407, describes old split behavior, and still references an xterm WebGL client renderer that was removed to fix corruption. Reviewers cannot distinguish current achievement from legacy claims.
- **Fix:** Replace the TODO with a 45–75 second silent demo and 3 annotated screenshots. Reframe the README opening as problem → constraints → pivotal design decisions → architecture → verification. Update only evidence-backed counts and renderer/layout claims.
- **Suggested command:** `$impeccable document`

### [P2] Operator density is being used as portfolio composition

- **Why it matters:** The density is correct for daily use but weakens the first screenshot. The left rail, top session strip, right status board, bottom deck, and terminal all compete for a recruiter's first 10 seconds.
- **Fix:** Make Showcase mode provide a presentation preset: curated two/three-terminal composition, safe labels, collapsed secondary navigation, intentional subject text, and a reset button. Preserve the normal operator UI unchanged.
- **Suggested command:** `$impeccable distill`

### [P3] Final design-system and language drift

- **Why it matters:** Mixed Korean/English labels and small inline token deviations are not serious usability defects, but they are visible signs of unfinished final-mile craft in a portfolio review.
- **Fix:** Choose one UI language for the showcase, move the remaining inline font/radius/color values onto committed tokens, and reconcile DESIGN.md's radius schema with its prose.
- **Suggested command:** `$impeccable polish`

## Persona Red Flags

**Engineering hiring manager:** The initial screen demonstrates complexity and taste, but the README provides no finished demo, before/after evidence, or concise explanation of the hardest technical decisions. They may conclude “impressive personal dashboard” without understanding terminal restoration, WebSocket/SSE separation, renderer corruption work, state inference, or interaction design depth.

**First-time developer:** The primary path is unclear among the icon rail, six session tabs, six status entries, and utility controls. The shortcut guide helps after discovery, but there is no guided first run showing “jump → group → prompt.” They may admire the surface without learning the core workflow.

**Security-conscious reviewer:** A live capture can expose active project names and terminal content. Without a deterministic redacted mode, sharing the strongest visual proof is also the highest privacy risk.

## Minor Observations

- The screenshot's terminal content can visually dominate with a large ANSI background color; a curated showcase fixture should use deliberate output that demonstrates readability rather than accidental color blocks.
- The current README's feature inventory is thorough but buries the product thesis and strongest differentiators below installation detail.
- A short architecture animation is unnecessary. One static diagram plus a real interaction recording will be more credible.
- Do not add more decorative motion to the working terminal UI. A polished demo edit is safer than reintroducing layout motion after prior stability issues.

## Questions to Consider

- Is the primary portfolio audience an engineering hiring manager, an open-source user, or both?
- Should the first public artifact sell the interaction design (canvas/grouping), the systems engineering (PTY/WebSocket/SSE/restoration), or a balanced two-part story?
- Would a separate deterministic Showcase mode be acceptable, or must every screenshot come from the real operating state?

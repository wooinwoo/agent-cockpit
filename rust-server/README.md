# Cockpit Rust 서버 전환

현재 사용자의 **Linux/WSL 운영 서버는 Rust로 전환됐습니다**. 2026-10-08 실제 3847 포트의 release 서버와 관리 프로세스, 세션 8개, 기존 HTML, 인증 키 보존을 확인했습니다. Windows 로그인 자동 시작과 설치된 앱은 같은 WSL 서비스에 연결하며, Windows에서 연결 진단도 통과했습니다. 기존 HTML·CSS·JS·글꼴을 그대로 제공하며 API, PTY/WebSocket, 감독·작업자, 에이전트 및 백그라운드 실행을 Rust에서 처리합니다. Node 서버를 프록시하거나 내부에서 실행하지 않습니다. 새 설치 프로그램의 빌드 경로와 다른 운영체제의 네이티브 실행은 별도 작업으로 남아 있습니다.

`--root`는 UI 파일을 읽을 소스 경로이고, `--sandbox-dir`는 별도 저장소입니다. preview의 기본 포트는 OS가 선택한 임의 포트이며 loopback만 허용합니다. Linux/WSL에서는 별도 `--data-dir` 모드로 기존 Node 저장 경로와 tmux를 인계할 수 있습니다. 두 저장 모드는 함께 지정할 수 없습니다. 시작 로그에는 주소와 `productionReady: false`만 출력하며 토큰은 출력하지 않습니다.

preview의 격리는 저장소와 tmux socket의 분리를 뜻하며 OS나 자식 프로세스의 보안 sandbox가 아닙니다. 사용자가 요청한 터미널 및 계정 로그인 점검은 기존 Node 서버처럼 부모의 HOME·PATH·기타 환경을 상속합니다. 선택 계정에는 해당 provider 홈을 지정하고 다른 provider 홈과 CLAUDECODE를 제거합니다. 자동 검증은 최소 환경, 가짜 CLI와 인증 파일, 전용 임시 저장소를 사용합니다.

## 실행과 검증

```sh
cargo build --locked -j 2 --manifest-path rust-server/Cargo.toml
cargo test --locked -j 2 --manifest-path rust-server/Cargo.toml
node scripts/verify-rust-server.mjs
node scripts/verify-rust-terminals.mjs
```

같은 검증에 `--release`를 붙이면 최적화된 실행 파일을 사용합니다. Linux/WSL의 `npm start`와 `scripts/start-cockpit.sh`는 Rust release 실행 파일을 사용합니다. 파일이 없으면 빌드 안내와 함께 실패하며 Node로 자동 전환하지 않습니다. `npm run start:node`, `npm start -- --node`, 또는 셸 실행기의 `--node` 옵션으로 기존 Node 경로를 명시적으로 선택할 수 있습니다. Windows/macOS의 npm 명령은 네이티브 지원이 완료될 때까지 안내를 출력하고 기존 Node 경로를 유지합니다. 이미 실행 중인 서버와 같은 데이터를 두 서버에서 동시에 열면 안 됩니다. 현재 노트북의 서비스 설정은 `scripts/cockpit-prod.service`에 있습니다.

Node가 `process.execve`를 지원하는 Linux에서는 npm의 실행기 프로세스를 셸과 Rust 관리자로 교체하므로 실행기용 Node 메모리가 남지 않습니다. 이전 Node 버전에서는 종료 신호와 종료 코드를 전달하는 자식 실행 방식을 사용합니다. `node --test tests/lib/start-cockpit.test.js`는 실행 경로·공백과 따옴표가 있는 경로·종료 코드·종료 신호를 검증합니다. Windows/macOS 항목은 분기 시험이며 해당 OS에서의 네이티브 실행 검증은 아닙니다.

Linux GNU 빌드는 Tokio를 시작하기 전에 glibc 메모리 할당 영역을 하나로 제한합니다. 반복 폴링을 서로 다른 작업 스레드가 처리할 때 큰 임시 메모리가 여러 영역에 남는 현상을 줄이기 위한 설정입니다. 실행 환경에 `MALLOC_ARENA_MAX` 또는 `GLIBC_TUNABLES`의 `glibc.malloc.arena_max`가 지정돼 있으면 그 설정을 유지합니다. 자식 AI의 환경 변수는 바꾸지 않습니다. [glibc의 `M_ARENA_MAX` 설명](https://sourceware.org/glibc/manual/2.31/html_node/Malloc-Tunable-Parameters.html)을 참고하세요. 이 설정은 전체 앱의 메모리 상한이나 장시간 누수 방지를 보장하지 않습니다.

`docs/_local/measure-cost-memory.mjs --release --line-kib=1 --rust-only --check-growth`는 별도 합성 기록으로 실제 비용 집계를 세 번 수행합니다. 마지막 반복에서 작은 기록 추가만으로 RSS가 다시 8 MiB 이상 늘면 실패하며, 집계 결과와 검증 프로세스 정리도 확인합니다. 운영 세션이나 고객 기록은 사용하지 않습니다.

비교 검증은 현재 작업 트리의 Node 서버를 임시 폴더와 임의 포트에서 실행합니다. Rust 서버에는 다른 빈 저장소를 할당합니다. 실제 프로젝트·계정·토큰·세션·보드를 복사하지 않습니다. 검증이 끝나면 두 검증 서버와 임시 폴더를 정리합니다.

```sh
rust-server/target/debug/cockpit-server \
  --root /absolute/path/to/claude-code-cockpit \
  --sandbox-dir /absolute/path/to/empty-preview-directory
```

`/api/migration/status`에 구현한 경로 목록이 있습니다. 현재 등록 경로 178개를 구현했습니다. 마지막 `POST /api/server/restart`는 관리 실행기와 함께 별도 통합시험을 통과했습니다. Pretendard와 JetBrains Mono의 원본 바이트·MIME·캐시 설정을 유지합니다. 미구현 API는 HTTP 501을 반환합니다. 이 경로 수가 실제 운영과 UI 전체 검증 완료를 뜻하지는 않습니다. 프로젝트의 `session`·`git`·`prs` 캐시와 비용·활동 정보의 실시간 갱신을 제공합니다.

## 기존 저장 경로와 터미널 인계

`--data-dir`는 기존 데이터 폴더를 사용하며, 새 설치에서는 없는 폴더를 권한 0700으로 생성합니다. 기존 폴더 권한은 바꾸지 않습니다. `--home-dir`는 기존 사용자 홈이며 생략하면 `HOME`을 사용합니다. 이 모드는 Linux/WSL에서만 허용합니다. 기본 바인드는 `COCKPIT_BIND` 또는 `0.0.0.0`, 포트는 `COCKPIT_PORT` 또는 3847이며 `--bind`로 지정할 수 있습니다. 먼저 포트를 확보하므로 같은 포트를 Node가 사용 중이면 저장소를 열기 전에 실패합니다. 데이터 폴더의 native 잠금은 다른 Rust 실행만 차단하므로 Node와 Rust를 서로 다른 포트로 같은 데이터에 연결하면 안 됩니다.

구 설치 폴더에만 남은 `.encryption-key`, `.cockpit-token`, `projects.json`, `jira-config.json`, `ai-config.json`, `session-state.json`, `agent-history.json`은 데이터 폴더에 해당 파일이 없을 때만 권한 0600으로 원문 복사합니다. 원본과 이미 존재하는 목적지 파일은 유지합니다. 잠금 후 암호화 키부터 이관하고 링크·비정규 파일을 거절합니다. 프로젝트·보드·계정 등록·AI 설정·암호화 키·터미널 상태·대화 기록은 데이터 폴더를 사용합니다. 노트·Telegram 설정·workflow·일정·비용 캐시는 기존 설치 폴더를 사용합니다. 세션·통계·계정 탐색은 사용자 홈을 사용하며, 위임 보고와 업로드는 기존 임시 폴더를 사용합니다. `COCKPIT_BOARD_FILE`의 상대경로도 작업 디렉터리를 기준으로 해석합니다. 기존 인증 토큰과 암호화 키를 재사용하며 손상된 값을 조용히 교체하지 않습니다.

`node scripts/verify-rust-startup.mjs --release`는 임시 HOME에서 기본 실행 명령으로 Rust 관리자를 시작합니다. 빈 설치, 새 토큰 권한, 재시작, 구 설치의 7개 파일 보존, 암호화된 설정의 실제 HTTP 조회, 기존 목적지 우선과 자식 프로세스 종료를 검증합니다.

읽기 전용 프로그램 폴더에서 실행하는 설치판은 `--data-dir`와 함께 `--state-dir /absolute/existing/user-state`를 지정할 수 있습니다. 노트·Telegram 설정·워크플로 실행 기록·일정·비용 캐시와 관리자 로그를 이 사용자 폴더에 저장하며, HTML·CSS·JS·워크플로 정의는 계속 `--root`에서 읽습니다. 실행기가 먼저 만든 기존 절대 디렉터리만 허용하고 심볼릭 링크를 거절합니다. 생략하면 종전 저장 위치를 그대로 사용합니다. 이 옵션은 기존 설치 폴더의 자료를 자동 이관하지 않으므로 기존 설치 전환 시 별도 보존 절차가 필요합니다. preview에는 지정할 수 없습니다.

같은 startup 검증은 설치 폴더를 실제 0555 권한으로 바꾸고 일반 사용자로 실행하여 원본 HTML 제공, 별도 노트·로그 저장, 재시작 후 노트 복원과 설치 폴더 불변을 확인합니다. `.github/workflows/ci.yml`의 `native` 작업은 Rust 단위시험과 release 빌드 후 startup·handover 검증을 실행합니다.

tmux는 상속된 socket 환경을 사용하여 기존 pane에 재접속합니다. preview는 계속 별도 저장소와 socket을 사용합니다. WSL 계정 탐색은 명시한 Windows 홈과 추정 경로를 확인하고, 필요한 경우에만 2초 제한으로 Windows 홈을 조회합니다. preview는 이 조회를 실행하지 않습니다.

`scripts/verify-rust-handover.mjs`는 전용 임시 파일과 가짜 계정으로 Node에서 Rust로 전환한 뒤 Node로 되돌립니다. 같은 포트·pane PID·터미널 ID·별칭·현재 폴더·셸 환경·일회성 명령의 단일 실행, 양방향 파일 수정, 토큰·암호화 키 보존과 preview 분리를 검증합니다. 전체 HTTP 검증도 이 시험을 실행합니다. 실제 운영 인계 결과는 `docs/_local/rust-production-cutover.json`에 기록합니다.

## 관리 실행기와 복구

Linux/WSL에서 실행 인자의 맨 앞에 `--managed`를 붙이면 Rust 관리자가 서버 자식 하나를 소유합니다. HTTP 및 Telegram 재시작은 복원 완료, 살아 있는 tmux, 실행 중인 개발 서버 없음, 체크포인트 저장과 관리자 연결을 확인한 뒤 종료 코드 75로 교체를 요청합니다. 일반 실행에서 재시작을 요청하면 HTTP 409로 관리 실행기가 필요함을 알립니다. Telegram 응답 전송이 실패하면 기존 서버를 유지합니다.

관리자는 실제 health 응답을 확인하고 기존 포트를 유지합니다. 비정상 종료는 1·2·4초 간격으로 최대 세 번 재시도합니다. 교체 후보가 시작에 실패하거나 60초 안정화 전에 비정상 종료하면 열어 둔 이전 실행파일로 한 번 복귀합니다. 관리자 종료는 자신이 생성한 서버만 종료하며 tmux 셸을 제거하지 않습니다. 관리자가 먼저 사라진 경우 기존 서버는 재시작 요청을 거절합니다.

관리 로그는 기존 경로 모드의 설치 폴더 또는 preview 저장소의 `logs/server.log`에 기록합니다. 파일 권한은 0600이고, 활성 파일과 이전 파일 각각 4 MiB로 제한하며 알려진 비밀값을 마스킹합니다. 서버 시작이나 health 실패를 무한 재시도로 숨기지 않습니다. 현재 운영 시작 프로그램은 `cockpit-prod.service`로 통일했으며, 서비스 종료는 관리자에게만 전달하여 tmux 프로세스를 함께 종료하지 않습니다.

Telegram `/diag`는 Rust RSS, 실제 폴링 위치, 대기 승인 수와 최근 로그의 오류·응답 시간을 표시합니다. V8 Heap은 해당 없음으로 표시합니다. 손상되거나 거절된 로그는 해당 항목만 확인 불가로 표시하고 나머지 진단을 유지합니다.

`scripts/verify-rust-manager.mjs`는 실제 HTTP 재시작, 강제 종료, 고장 난 후보 교체 두 번, health 확인 직후 종료되는 후보, 관리자 선종료, Telegram 응답 실패와 재시작 성공을 전용 프로세스로 검증합니다. 같은 pane·작업 폴더·셸 환경·체크리스트·토큰을 유지하고 처음 명령을 반복 실행하지 않는지도 확인합니다.

체크포인트 유지와 정상 종료 뒤에는 기존 `recovery-history` 형식도 저장합니다. 전체 보드와 세션 상태, 프로젝트 등록 정보, 한국어 요약을 보존하며 시간별 최초 파일은 변경하지 않고 최근 50개를 남깁니다. 원본 Node 내보내기 도구로 읽을 수 있습니다.

`node scripts/verify-portfolio.mjs --rust`는 실제 브라우저에서 터미널 그룹·순서·분할, 같은 셸과 작업 경로의 재시작 복원, 일반 PTY의 휠 스크롤을 검사합니다. `node scripts/verify-work-overview-layout.mjs --rust`는 열 가지 세로·좁은 창 크기에서 저장 버튼, 완료 항목을 포함한 체크리스트 50개와 근거 영역의 접근·가로 잘림을 검사합니다. 두 검증은 전용 가짜 프로젝트를 사용합니다. 필요한 경우 `CHROME_BIN`으로 설치된 Chromium 경로를 지정합니다.

## AI 설정·대화 기록·포트 검증

AI 설정은 기존 `ai-config.json`, `.encryption-key`, `enc:iv:tag:ciphertext` AES-256-GCM 형식을 사용합니다. Node가 저장한 키를 읽고 Rust가 저장한 키를 Node가 다시 읽을 수 있습니다. 키·설정·백업은 0600으로 저장하며 기존 설치 키를 재사용합니다. 손상되거나 누락된 암호화 키로 기존 설정을 조용히 덮어쓰지 않습니다. 이전 평문 설정을 백업할 때도 API 키는 암호화하고 추가 필드는 보존합니다. 정상 백업 10개를 정리 대상으로 유지하며 의심 경로를 따라가지 않습니다. 저장 이후 백업 정리 실패가 저장 성공 응답을 뒤집지 않습니다.

설정 조회는 마지막 UTF-16 네 단위만 표시합니다. Gemini 연결 시험은 원본 모델·본문을 사용하고 10초 뒤 종료하며, 오류에 요청 URL이나 반사된 키를 노출하지 않습니다. 자동 검증은 `COCKPIT_PREVIEW_GEMINI_BASE`의 loopback HTTP 모의 서버만 사용하며 실제 Google 요청을 보내지 않습니다.

에이전트 대화 목록·조회·생성·삭제, 모델 선택, 사용자 이름, 팀·프로필·회사 정보 API를 제공합니다. 대화 생성 시 7일 보관·최대 50개 정책을 적용하며 저장 시 대화별 최근 메시지 100개를 보존합니다. UTF-16 미리보기, 같은 시각의 안정 정렬, 숫자 키 순서와 추가 메시지 필드를 유지합니다. 동기 로드와 원자 저장으로 시작 시 읽기 경합 및 동시 저장 손실을 방지하며 손상 파일은 오류로 알리고 보존합니다. 모델 선택과 사용자 이름은 원본처럼 메모리에만 있습니다. 프로필 데이터는 원본을 추출한 JSON을 Rust에 포함하고 비교 시험에서 일치 여부를 검사합니다. `claudeAvailable`은 원본처럼 CLI 어댑터를 나타내며 로그인 여부를 뜻하지 않습니다. 실제 chat·stop·도구 실행·오케스트레이션은 native 실행기로 연결했습니다. `verify-rust-agent-core.mjs`가 원본에서 추출한 계약과 Rust 단위시험을, `verify-rust-agent-runtime.mjs`가 전용 HTTP·SSE·가짜 provider 실행과 취소를 검증합니다. 감독 모니터와 일정 실행, Telegram 명령·에이전트 연결도 별도 통합 검증에 포함하며 실제 외부 서비스 가용성 검증과 구별합니다.

Unix 포트 조회는 `lsof`와 `ss` 대체 경로, `ps` 프로세스 이름, 중복 제거·정렬·개발 서버 표시를 유지합니다. 이름 조회는 최대 8개를 동시에 처리합니다. 명시적 종료는 인증·CSRF 및 localhost 검사를 통과한 양수 PID에만 SIGTERM을 보냅니다. 원본의 보호 PID에 PID 1을 추가하고 정수 변환으로 프로세스 그룹을 종료하지 않도록 범위를 검사합니다. Windows 포트 관리는 아직 501입니다.

`node scripts/verify-rust-agents.mjs`는 격리된 저장소·가짜 조회 CLI·모의 Gemini 서버로 비교합니다. 종료 시험은 직접 생성한 시험용 sleep 프로세스에만 신호합니다. 같은 검증을 전체 HTTP 비교에도 포함합니다.

## 설정·탐색·브리핑·배치 검증

설정 내보내기는 저장된 프로젝트만 반환합니다. 가져오기와 탐색 결과 추가는 기존 ID 생성·색상·허용 필드 규칙을 따르고, 경로의 슬래시 및 대소문자를 정규화하여 중복을 거릅니다. 가져오기는 전체 입력 검증 후 한 번 저장하므로 뒤쪽 항목이 잘못되어도 앞쪽 항목만 남지 않습니다. 동시에 같은 경로를 가져와도 한 프로젝트만 생성합니다.

프로젝트 탐색은 preview 홈의 기본 폴더, 운영자가 지정한 `COCKPIT_PROJECT_ROOTS`, 격리된 Claude 기록을 합칩니다. Git 폴더 깊이 제한·제외 폴더·기존 프로젝트 제외·세션 수·최근 시각을 유지하고 ICU로 locale별 이름 정렬을 처리합니다. preview 홈의 기록은 외부 symlink를 따르지 않습니다. 명시한 탐색 루트는 preview 저장소 밖일 수 있습니다. Windows WSL 배포판 자동 탐색은 아직 남아 있습니다.

브리핑과 알림은 기존 활동·비용 임계값, 현지 날짜, 우선순위 및 이전 날짜 스냅샷을 사용합니다. 시작 시 당일 스냅샷을 한 번만 저장하며 조회는 스냅샷을 바꾸지 않습니다. 알림 설정의 추가 필드를 보존하고 저장 실패는 오류로 반환합니다. 원본의 잘못된 `prs:` 캐시 참조는 실제 PR 캐시로 연결했습니다. 비-Unix 환경의 날짜는 아직 UTC이므로 Windows 현지 날짜 지원은 별도 검증이 필요합니다.

배치는 기존 12개 명령 목록과 최대 5개 동시 작업, 상태 조회·SSE·명시적 중지를 지원합니다. HTTP 연결이 끊겨도 접수한 작업을 추적합니다. 중지는 실행 중인 명령이 끝나도록 두고, 공유 명령 슬롯을 기다리던 작업도 새로 실행하지 않습니다. 중지 확인과 프로세스 생성은 같은 잠금으로 직렬화합니다. 원본에서 성공 출력 객체에 `.slice()`를 호출하던 오류는 실제 stdout을 사용하도록 고쳤습니다.

`node scripts/verify-rust-controls.mjs`는 별도 저장소와 가짜 명령으로 설정·탐색·브리핑·배치를 비교합니다. 순차·병렬 실행, 중지, 요청 연결 종료, 출력 제한과 기록 보존을 확인합니다. 명령 슬롯 포화 상태의 중지·서버 종료는 별도 Rust 단위시험으로 검증합니다. 같은 HTTP 검증을 전체 비교에도 포함합니다.

## 개발 서버·파일·시스템 검증

개발 서버 시작·중지·목록과 최초 포트 탐지를 처리하고 `dev:status` 및 SSE 초기 상태에 연결합니다. Linux에서 실행마다 별도 process group을 만들며 명시적 중지·자연 종료·서버 종료 시 해당 그룹을 정리합니다. 종료된 leader를 정리 전에 reap하지 않으므로 재사용된 PID에 신호하지 않습니다. 종료 감시는 실행별 객체를 확인하여 이전 실행이 새 실행 기록을 지우지 않습니다. 별도 세션으로 그룹을 탈출하는 프로그램과 Windows/macOS 개발 서버 처리는 아직 지원하지 않습니다.

등록 프로젝트 파일 미리보기는 2 MiB, 클립보드 및 multipart 업로드는 10 MiB로 제한합니다. 원본 바이트·확장자·응답 형식을 보존하고 preview 저장소 안에 파일을 0600으로 생성합니다. 파일 경로는 원본과 정규화 경로의 실제 부모를 함께 확인하여 symlink와 없는 중간 폴더를 사용한 범위 이탈을 거부합니다. Linux에서는 읽기 전에 실제 열린 파일 descriptor의 경로도 확인하여 검사와 열기 사이의 부모 디렉터리 교체를 방어합니다. 다른 플랫폼의 descriptor 경계 검증은 아직 미구현이며 파일 미리보기를 허용하지 않습니다. 오래된 paste 파일은 시작 5초 후와 30분 간격으로 정리하며 일반 업로드와 외부 symlink 대상은 삭제하지 않습니다.

프로젝트·파일 IDE 열기, URL·폴더 열기를 Linux/macOS 명령 인자로 전달하며 셸 문자열로 합치지 않습니다. 누락된 실행 파일의 성공 응답은 원본의 fire-and-forget 계약이며 실제 GUI 표시를 보증하지 않습니다. Windows 실행기는 별도 quoting 검증까지 501입니다. health는 Linux의 실제 RSS, 실행 시간, 프로젝트·터미널·SSE 연결 수를 반환합니다. `/proc` 없는 플랫폼의 메모리 측정은 아직 남아 있습니다.

CI 실행 목록·상세·작업·로그·재실행·취소와 workflow 목록을 기존 `gh` 인자로 처리합니다. 60초 목록 캐시와 재실행·취소 후 무효화, 숫자 run ID 검증, 실패 시 로그 대체 문구를 유지합니다. 캐시는 원본과 같이 limit query를 키에 포함하지 않으며, 메모리 누적 방지를 위해 최대 256개 항목을 유지합니다.

`node scripts/verify-rust-system.mjs`는 임시 서버, 가짜 IDE·브라우저·GitHub 명령과 포트를 열지 않는 시험 프로세스로 비교합니다. 업로드 바이트와 크기 경계, 경로 이탈, SSE, 자식 프로세스 정리 및 연속 재시작을 검증합니다. 실제 PR·CI·사용자 개발 서버·GUI는 실행하지 않습니다. 같은 검증을 전체 HTTP 비교에도 포함합니다.

## 세션 기록·비용·활동 검증

Claude JSONL과 OpenCode SQLite의 세션 상태·목록을 합칩니다. OpenCode DB는 읽기 전용으로 열고, 기록 없는 프로젝트·빈 기록·작업 중·응답 대기·유휴 상태와 더 활동적인 provider의 우선순위를 유지합니다. 프로젝트별 5초 polling과 `session:status` SSE, 초기 캐시를 연결합니다. 완료 알림과 세션 실행·재개 계획은 native로 연결했으며 실제 비-Linux 데스크톱 동작은 플랫폼 검증이 남아 있습니다.

채팅 기록은 이미지·도구 결과·thinking·토큰 분류를 보존합니다. 제목은 첫 50줄에서 찾고 UTF-16 60자, 메시지 미리보기는 최근 200개, 타임라인은 앞 500개 이벤트를 표시합니다. 제한 밖의 사용량과 파일 변경도 집계합니다. JSONL은 줄 단위로 읽으며 메시지 미리보기에서 원본 이미지와 전체 기록을 메모리에 쌓지 않습니다. 32 MiB 이미지 기록을 읽는 별도 회귀 시험으로 메모리 증가를 확인합니다.

위임 작업은 localhost 상태 보고와 preview 저장소의 `delegate-status` 파일로 수신합니다. 터미널 프로젝트 또는 가장 깊은 cwd 일치로 연결하고, 수신 시각 기준 15초 heartbeat 만료·완료 보고를 적용합니다. 파일은 시각·형식을 검증하고 소비합니다. preview는 운영 임시 폴더에 접근하지 않으며 `--data-dir` 모드는 기존 `cockpit-delegates-<uid>` 경로를 사용합니다. 자동 비교용 Node fixture도 별도 TMPDIR을 사용합니다.

비용은 기존 모델 계열별 계산, 메시지 중복 제거, 로컬 날짜·주간 리셋, 30일 이력, 알 수 없는 모델의 추정 표시와 세션별 분석을 유지합니다. 메모리 캐시는 30초, 비용 SSE는 60초, 활동 SSE는 10초입니다. 기존 크기 기반 증분 캐시도 유지하므로 같은 크기의 파일 덮어쓰기와 당일 집계가 완전히 비는 경우의 기존 stale 동작은 남아 있습니다. 가격은 원본 구현의 API 환산 추정치이며 현재 청구 단가를 새로 확인한 값은 아닙니다.

preview는 `home/.claude`와 `home/.local/share/opencode`만 사용하며 외부 경로·symlink를 거부합니다. 기존 객체 입력의 JSON 문자열 투영은 Rust 공용 객체 정렬로 키 순서가 달라질 수 있으며 값은 보존합니다. 일부 비정상 기록은 원본의 전체 요청 실패 대신 해당 항목을 건너뜁니다. `rust-session-checks.js`, `rust-delegate-checks.js`, `rust-cost-checks.js`는 가짜 기록·DB·사용량으로 원본 응답과 실제 타이머를 비교합니다.

## Git·PR 검증

Git 상태·브랜치·diff·로그·stash 조회와 스테이징·되돌리기·커밋·브랜치 변경·push·pull·fetch·stash·선택 파일 자동 커밋 실행을 처리합니다. 프로젝트별 변경 명령을 직렬화하고 전체 Git/GitHub 명령 동시 실행을 8개로 제한합니다. diff는 5 MiB까지 읽고 기존처럼 화면에는 3000줄을 제공하며 전체 파일 통계를 보존합니다. 커밋 메시지 생성과 AI 자동 커밋 계획도 원본 계약 및 전용 provider 시험으로 검증합니다.

PR 목록·전체 목록·상세·diff·승인·변경 요청·댓글·병합은 기존 GitHub CLI 인자를 사용합니다. 전체 목록 정렬, 누락 필드와 한글·UTF-16 데이터, 조회 실패 시 빈 목록과 작업 실패 응답을 보존합니다. 검증은 가짜 `gh`만 실행하며 실제 PR을 수정하지 않습니다. Git 검증도 임시 저장소와 로컬 bare remote만 사용합니다.

Git은 30초, PR은 120초마다 확인하고 polling 배율은 1~10입니다. 처음에는 브라우저 없이도 캐시를 만들며, 캐시가 있고 SSE 연결이 없으면 재조회를 생략합니다. 동일 결과는 다시 방송하지 않습니다. 프로젝트 경로 변경 시 새 경로로 전환하고 삭제·서버 종료 시 해당 조회를 취소합니다. SSE는 구독 후 초기 캐시를 읽어 연결 중 갱신 누락을 막고, 느린 연결이 버퍼를 넘으면 종료해 EventSource 재연결로 최신 초기 상태를 받게 합니다.

의도적인 차이: Git 파일 목록은 문자열 배열만 허용하고 `-`로 시작하는 브랜치 이름은 옵션으로 실행하지 않습니다. 기본 stash 메시지의 시각은 시스템별 locale 대신 ISO 형식입니다. 기존 혼합 파일 되돌리기의 성공 응답 등 다른 Git 동작은 Node 비교로 유지합니다. `tests/helpers/rust-git-checks.js`와 `rust-github-checks.js`를 HTTP 비교 검증에 포함합니다.

## 보드 저장 검증

보드 조회·전체 콘텐츠 저장, 감독 생성·감독별 조회, 메모 변경·추가, 작업과 양방향 질문의 생성·수정·삭제를 native Rust에서 처리합니다. 작업 완료와 질문 답변을 별도로 보존하며 삭제한 작업의 ID를 다시 사용하지 않습니다. 기존 편집기가 질문 수신자나 세션 ID를 빠뜨려도 저장된 값을 유지합니다.

Node와 동일한 파일 잠금 규약을 사용하고 잠금을 얻은 뒤 최신 파일을 다시 읽습니다. 저장은 임시 파일·fsync·원자적 교체를 거칩니다. 살아 있는 CLI 작성자의 잠금을 빼앗지 않으며 종료된 작성자의 잠금만 복구합니다. 손상 파일과 symlink는 덮어쓰지 않습니다. 오래된 편집 내용은 세 방향 병합으로 합치며 같은 필드의 충돌은 409로 알립니다. 콘텐츠 저장으로 최신 감독·작업자 실행 토큰과 보고 상태를 되돌리지 않습니다.

`tests/helpers/rust-board-checks.js`를 HTTP 비교 검증에 포함했습니다. 기존 형식, 한글·이모지·단독 surrogate, 질문 방향, 동시 편집 충돌, 감독별 범위, 완료 기록 50개 제한, 손상 파일 보존과 기존 Node CLI 작성자/Rust HTTP 작성자의 동시 저장을 비교합니다.

감독·작업자 제어 API는 권한 프리셋과 감독 설정, 작업자 목표·우선순위·일시정지, 독립 진행 모드, 재개 요청, 감독·작업자 보고를 저장합니다. 보고와 설정은 콘텐츠 revision을 변경하지 않습니다. 최신 설정과 토큰을 파일 잠금 안에서 검증하고, 다른 실행 중인 감독과 작업자 소유권이 겹치면 거부합니다. 감독 중지와 독립 작업자 중지를 구별하며 사용자 일시정지·기한 만료는 보고 토큰과 재개 요청보다 우선합니다.

작업자의 완료 주장은 `reported`로 남고 감독의 근거 확인을 거쳐 `complete`가 됩니다. 결과물·버전의 SHA-256 식별자는 기존 Node와 동일하며 A→B→A 중복 보고로 진전 시각을 갱신하지 않습니다. 모든 남은 조건과 독립 대안 검토를 기록하지 않은 전체 대기는 거부합니다. `tests/helpers/rust-board-control-checks.js`에서 기존 Node API와 응답·저장·오류 시 파일 보존을 비교합니다.

터미널 관측은 최대 8개를 동시에 조회하며 보드 파일 잠금을 잡기 전에 수행합니다. 유효한 tmux·실행 명령·현재 AI가 일치할 때만 복구 설정을 저장합니다. 빈 터미널에서 직접 실행한 AI는 현재 종류로 기본 복구 명령을 계산하며 승인 생략 권한을 추정하지 않습니다. 아래 점검·복구 검증을 운영 무인 자동화 전체의 검증으로 해석하면 안 됩니다.

작업자 실행기는 15초마다 저장된 배정을 확인합니다. `workerDispatch=running`은 감독이 중지되어도 독립 실행하며, `linked`는 감독 상태를 따릅니다. 우선순위를 지키고 개별 일시정지·대화 보호·운영 기한·완료 보고를 확인합니다. 같은 빈 입력창이 15초 이상 유지되어야 작업을 전달하고, 토큰·시도 시각을 저장한 뒤 PTY 작성자가 최신 전체 감독 설정을 다시 비교합니다. 변경된 목표나 만료된 배정으로 전달하지 않습니다.

막힌 조건의 답변·동료 결과가 바뀌면 재개할 수 있으며, 같은 의존성에는 2분 대기 시간을 유지합니다. 5분 동안 새 검증 근거가 없으면 감독 확인을 요청하고, Codex의 빈 입력창이 확인된 실행 중 작업에는 중복하지 않는 점검 메시지를 예약합니다. 사용자 요청으로만 일시정지 목표를 재개하며 `/goal resume`를 배치한 뒤 다음 점검에서 그 정확한 입력창을 확인하고 Enter를 보냅니다. 재개 요청과 확인에도 만료 시간을 적용합니다.

첫 작업자 점검은 브라우저 연결 없이 저장된 터미널을 복원합니다. 기존 pane을 다시 연결하며 목표·토큰·일시정지·재전달 대기 시간을 유지합니다. 종료 신호 이후에는 새 자동 입력을 접수하지 않습니다. `node scripts/verify-rust-terminals.mjs --workers-only`는 실제 15초 타이머와 전용 가짜 Codex로 독립 배정·우선순위·완료 보류·의존성 변화·명시적 재개·정체 점검·기한 종료·브라우저 없는 재시작을 검증합니다. 작업 지시 전체 바이트도 격리된 Node 원본과 비교합니다. 이 검증은 실제 외부 업무의 완료나 무기한 가동을 보증하지 않습니다.

감독별 점검도 별도의 15초 타이머에서 실행합니다. 하나의 미확인 점검과 재촉 간격, 작업자 근거 부족 알림, 전체 지시문, 보고 확인과 종료 시간을 기존 보드 계약에 맞춰 처리합니다. 점검 입력은 최신 감독 전체 상태와 현재 AI를 다시 확인한 뒤 접수합니다. 감독 관측·재시작 대기로 독립 작업자 타이머를 멈추지 않습니다.

자동 복구를 켠 감독은 종료된 AI와 설정한 보고 기한을 넘긴 AI를 저장된 명령 그대로 `respawn-pane`으로 실행합니다. 새 권한 옵션은 추가하지 않습니다. 정상 AI, 다른 종류로 바뀐 AI, 사용자 대화 보호, 일시정지·승인·제한 화면은 중단하지 않습니다. 프로세스나 현재 화면 상태가 불명확한 경우도 복구를 보류하며 사용자 초안을 보호합니다. 복구 직전에 기한·프로세스·전체 감독 설정을 다시 확인합니다. 세 번 복구해도 보고가 없으면 기한 안에서 5분 쉬고 재시도합니다.

터미널 명시적 종료는 관련 감독을 먼저 중지하고 자동 복구를 끕니다. 이미 사라진 터미널 ID에도 적용합니다. 서버 재시작은 기존 pane을 다시 연결하고, 사라진 pane은 고정 ID로 복원한 뒤 한 번만 실행합니다. `node scripts/verify-rust-terminals.mjs --supervisors-only`는 전용 가짜 AI와 실제 타이머·tmux로 감독 지시문 전체 바이트, 보호 상태, 종료·정체·pane 유실 복구, 보고·목표 보존, 기한 종료, 브라우저 없는 재시작과 명시적 종료를 검증합니다.

## 터미널 연결 검증

- native PTY에서 생성, 원문 입력 및 접수 응답, 출력, 종료를 처리합니다. WebSocket Host·Origin·토큰 검사를 유지합니다. 크기 변경은 현재 소유 창만 처리하며 focus·연결 종료 시 소유권을 넘깁니다.
- 검증 저장소 아래 전용 `TMUX_TMPDIR`를 사용합니다. 서버 종료는 클라이언트만 떼고 tmux pane은 유지합니다. 명시적 터미널 종료는 해당 전용 socket만 종료합니다.
- 한글·이모지의 UTF-8 바이트 분할을 처리하고 재접속 출력에서는 OSC 52 클립보드 명령을 제거합니다. 재접속 시 출력 snapshot과 구독을 같은 잠금으로 연결합니다.
- 고정 ID·별칭·현재 폴더·알 수 없는 checkpoint 필드를 저장합니다. 30초마다 현재 폴더를 갱신하고 복원 대기 항목을 재시도합니다. 비durable Linux 셸은 `/proc/<pid>/cwd`에서 현재 폴더를 읽습니다. 최초 연결 전 저장 상태는 빈 목록으로 덮어쓰지 않습니다.
- 프로세스가 살아 있으면 기존 pane에 다시 연결합니다. 냉간 복원에서는 검증된 AI 실행 명령만 재실행하며 이전 일회성 작업·로그인 명령은 자동 재실행하지 않습니다. 저장된 계정을 찾지 못하는 냉간 실행은 대기 상태로 보존합니다.
- 한글 프로젝트·터미널 ID를 유지하고 REST 경로의 percent encoding을 해석합니다. 복원 항목의 ID 또는 durable ID가 중복되면 기존 등록을 재사용합니다.

터미널 검증은 임시 프로젝트로 다중 창 크기 경합, 원문 입력, 한글 출력, 정상·강제 서버 종료, 같은 pane PID 유지, 냉간 복원, 일회성 명령의 중복 실행 방지, 주기적 복원 대기 해소와 비durable 폴더 보존을 확인합니다. 결과는 `docs/_local/rust-terminal-verification.json`에 기록합니다. 원본 Node와의 HTTP 비교 검증과는 별도이며, 터미널 기능 전체의 동등성을 뜻하지 않습니다.

터미널 활동 상태는 Linux `/proc`의 실제 foreground process group과 tmux 현재 화면을 대조합니다. Claude·Codex·jcode·opencode 실행 파일과 interpreter launcher를 구분하며, `vim jcode` 같은 파일 인수나 멈춘·백그라운드 AI를 실행 중으로 취급하지 않습니다. 2초마다 `agent-status`를 갱신하고 `/api/terminals?activity=1`에는 새로 관측한 상태와 시각을 반환합니다. 현재 pane 조회 실패는 unknown이며 과거 replay의 승인창으로 대체하지 않습니다. 일반 셸은 offline, tmux 없는 AI의 화면 판단은 unknown입니다. REST `/screen`은 기존 계약대로 replay 기록을 반환합니다.

`tests/fixtures/rust-activity.json`의 같은 화면 사례를 Node 원본과 Rust 단위시험에서 함께 검증합니다. 실제 PTY 검증은 격리된 가짜 Claude·Codex·jcode와 일반 편집기 프로그램으로 작업 중·빈 입력창·승인창·초안·오류·일시정지·종료를 확인합니다. `node scripts/verify-rust-terminals.mjs --activity-only`는 이 구간만 실행하며 별도의 `docs/_local/rust-activity-verification.json`을 기록합니다.

활동 조회는 최대 8개를 동시에 관측하고 전체 관측 대기는 2초로 제한합니다. 개별 tmux 조회 제한은 1초입니다. 일부 관측이 멎어도 끝난 결과는 정상 반환하며 미완료 항목은 unknown으로 남깁니다. 검증에서는 전용 시험 tmux 서버 3개만 일시정지해 정상 세션이 UI의 3초 제한 안에 갱신되는지 확인하고, `finally`에서 시험 프로세스를 재개합니다.

REST 자동 입력은 현재 AI 프로세스와 tmux 화면을 확인하고 승인창·초안·일시정지·일반 셸로의 작업 메시지를 거부합니다. 명시적인 제어 키 입력에는 별도 상태 검증을 적용합니다. 조회 중 사용자 키 입력이나 대화 보호가 시작되면 자동 전달을 취소합니다. 감독 요청은 파일 잠금 안에서 최신 보고·배정 시각과 기한을 확인합니다. 잠금 경합은 화면 관측이 낡지 않도록 즉시 503을 반환하며, 입력 접수가 8초 안에 끝나지 않으면 대기열에서 나중에 실행하지 않습니다. 성공 응답은 PTY 작성자의 접수이며 AI의 처리 완료를 뜻하지 않습니다.

대화 보호는 관련 감독의 일정과 작업자의 재개 시각을 갱신하고 기존 작업 토큰을 보존합니다. 해제 저장에 실패하면 보호 상태를 유지하며, 실패한 보호 설정을 같은 값으로 재시도해도 저장 전에는 성공으로 응답하지 않습니다. 보호는 새 자동 입력 접수를 차단하며, 이미 접수된 입력의 쓰기를 회수하지는 않습니다. PTY 쓰기가 막혀도 보호 저장 잠금을 계속 잡지 않습니다. 실행 명령 등록은 현재 AI와 기존 명령을 대조하고 checkpoint에만 저장합니다. 이미 등록된 자동 복구 명령과 충돌하면 거부하며 명령을 PTY에 입력하지 않습니다. `node scripts/verify-rust-terminals.mjs --input-only`는 전용 가짜 AI로 실제 전달 바이트, 동시 사용자 입력, 감독 CAS, 대화 보호와 저장 실패를 검증합니다.

세션 기록의 주기적 관측은 연결되어 있습니다. Windows 실행과 실제 운영 세션 인계는 별도 검증이 필요합니다.

## 계정과 승인 감시 검증

저장 계정의 생성·삭제·로그인 점검·예산 변경을 native Rust에서 처리합니다. 기존 배열 및 객체 형식과 알 수 없는 필드를 보존하며, 손상된 메타데이터는 덮어쓰지 않습니다. 계정 폴더는 0700, 메타데이터는 0600으로 저장합니다. 삭제는 소유한 계정 폴더에만 적용하며 외부 경로와 symlink 대상은 지우지 않습니다.

계정을 지정한 터미널은 해당 provider와 계정 홈으로 실행합니다. 저장된 권한 프리셋은 일반 provider 실행에 적용하고, 명시적인 로그인 및 사용자 지정 명령에는 추가하지 않습니다. 기존 pane은 계정 메타데이터가 사라져도 다시 연결합니다. pane까지 사라졌다면 계정 복구를 기다리며, 계정이 돌아오면 provider를 실행하고 이전 로그인 명령은 반복하지 않습니다.

계정 목록 GET은 저장 계정과 허브 계정을 함께 반환합니다. 원본 경로 기반 계정 ID, 허브의 48시간 한도 신선도와 주간 리셋 주기, credential 상태, 공식 한도·로컬 예산의 우선순위를 유지합니다. preview의 허브 파일 및 참조 계정은 검증 저장소 안에서만 읽습니다. `--data-dir` 모드에는 WSL의 Windows 홈 탐색을 연결했습니다. 가짜 실행기와 credential 경로로 검증했으며 실제 운영 credential 인계는 남아 있습니다.

사용량은 5분 캐시를 즉시 반환하고 중복 스캔 없이 백그라운드에서 갱신합니다. Claude의 최근 7일·5시간 토큰 집계, Codex의 최근 rollout 한도, 공식 HTTPS 한도 조회와 OAuth 토큰 갱신을 처리합니다. 401은 한 번 갱신한 뒤 재시도합니다. credential은 최신 파일의 추가 필드를 보존하고 0600 임시 파일로 교체하며, 갱신 중 다른 로그인으로 refresh token이 바뀌었으면 덮어쓰지 않습니다. 비짝 UTF-16 문자열이 포함된 기록과 인증 메타데이터도 보존합니다. 자동 검증은 가짜 토큰과 로컬 모의 OAuth 서버를 사용합니다.

계정 파일의 metadata를 500ms마다 확인하고 로그인·삭제·허브 프로필 변경을 `ai-accounts:changed` SSE로 전달합니다. credential 변경은 사용량 캐시도 무효화합니다. transcript 폴더는 이 감시에서 스캔하지 않습니다. `/api/events`는 초기 이벤트, 15초 keepalive, 최대 50개 연결과 종료 처리를 제공합니다. 세션·Git·PR·비용·활동 캐시와 개발 서버 이벤트를 제공합니다. 기존 `nodeVersion` 필드는 null입니다. SSE 연결·재연결·프로젝트 변경·알림의 전용 검증을 통과하여 이 경로도 구현 경로 수에 포함합니다. 실제 운영 연결 인계는 별도입니다.

`tests/helpers/rust-account-checks.js`와 `rust-account-list-checks.js`는 Node 원본과 HTTP 목록·사용량·파일 보존·계정 변경 알림을 비교합니다. `node scripts/verify-rust-terminals.mjs --accounts-only`는 가짜 Claude·Codex로 저장 및 허브 계정 선택, 권한 프리셋, 부모 provider 홈 정리, 로그인, 재접속과 브라우저 없는 복원을 검증합니다.

승인 감시는 상태 조회와 명시적 중지를 처리합니다. 전용 `approve-bot` socket에서 정해진 스크립트가 단독 실행 중인지 확인하며, 불명확하거나 멈춘 tmux는 unknown으로 표시합니다. 다른 프로그램에는 중지를 허용하지 않습니다. 스크립트 시작이나 승인 키 입력은 수행하지 않습니다. 검증에서는 실제 승인 스크립트 대신 전용 sleep 프로세스와 가짜 명령 결과를 사용합니다.

## 데이터와 인증 보존

- preview 최초 실행은 빈 저장소만 허용하며 marker와 파일 잠금으로 중복 실행을 차단합니다. `--data-dir` 모드는 기존 저장 경로를 사용하므로 위의 인계 조건을 따라야 합니다.
- 토큰은 별도 저장소에 0600으로 생성합니다. 재시작 시 재사용합니다. 손상된 토큰을 조용히 재발급하지 않습니다.
- 기존 Host 검사, proxy 헤더가 있는 loopback의 인증 요구, token/cookie, CSRF, 로그인·노트 생성 횟수 제한을 유지합니다. 광고된 네트워크 IP의 Host 허용과 인증은 전용 네트워크 검증에 포함합니다. preview 바인드는 loopback으로 제한합니다.
- 노트 저장은 임시 파일, flush/fsync, 원자적 교체 순서입니다. 부분 수정은 직렬화합니다. 손상 파일은 수정 시 덮어쓰지 않습니다. 명시적 삭제는 손상 파일에도 가능합니다.
- Node의 UTF-16 길이 제한을 따릅니다. 이모지 중간에서 잘린 문자열, 단독 surrogate, 모르는 추가 필드도 JSON 원문 값으로 보존합니다.
- 프로젝트 ID 충돌 처리, 이름에서 계산하는 기본 색상, CSS 색상 검증, 허용 필드만 수정하는 규칙을 유지합니다. 프로젝트 저장은 성공한 뒤에만 메모리에 반영하며 이전 파일을 최대 10개 백업합니다.
- 프로젝트 파일과 알 수 없는 추가 필드는 유지합니다. 일시적으로 사라진 드라이브의 프로젝트를 자동 삭제하지 않습니다. 손상된 프로젝트 파일은 시작 시 오류를 내고 보존합니다.
- ID가 없는 구형 프로젝트는 이름에서 ID를 보완합니다. 이름으로 만들 수 없으면 기존 base36 시각 형식을 사용합니다. 원본 파일을 백업하고 보완된 ID를 저장하므로 재시작할 때 ID가 바뀌지 않습니다.
- 경로 선택과 package scripts 조회는 실제 파일 경로를 기준으로 등록 프로젝트 범위를 확인합니다. 대소문자가 다른 별도 경로, `..`, symlink를 통해 등록 범위를 벗어나는 읽기는 허용하지 않습니다. localhost 경로 선택은 기존처럼 프로젝트 등록을 위해 전체 경로를 탐색할 수 있습니다.
- 노트 및 정적 파일의 symlink는 거부합니다. 정적 경로로 저장소나 임의 소스 파일을 제공하지 않습니다.
- 의도적인 오류 응답 차이: JSON 객체가 아닌 본문과 보드 JSON의 128단계 이상 중첩은 400, 10 MiB 초과는 413, 본문 수신 10초 초과는 408입니다. 깊이 제한을 넘는 저장 보드는 500으로 알리고 원본을 보존합니다. 검증되지 않은 기능에 성공 응답을 대입하지 않습니다.

## 운영 전환 조건

`node scripts/verify-rust-server.mjs --require-complete`는 현재 **실패해야 정상**입니다. 현재 개발 호스트의 운영 인계는 `docs/_local/rust-update-verification.json`에 기록되어 있지만, 배포 실행기와 다른 플랫폼 검증은 남아 있습니다. 일반 비교 검증 성공이나 한 호스트의 전환을 전체 플랫폼 전환 완료로 해석하면 안 됩니다.

검증 스크립트는 `server.js`와 `routes/*.js`의 등록 경로를 다시 읽어 미구현 목록을 `docs/_local/rust-migration-verification.json`에 기록합니다. 경로 개수만으로 아래 백그라운드 동작의 보존을 증명할 수는 없습니다.

| 검증 영역 | 보존해야 하는 동작 |
| --- | --- |
| 터미널·WebSocket | 기존 tmux pane 유지, 고정 ID·별칭, 출력 재연결, 입력 보호, 크기 소유권, 계정별 실행 환경 |
| 보드·감독·작업자 | revision/CAS, 파일 잠금, checklist·질문·목표, 독립 작업 재개, 대화 보호, 기한·재시도·복구 제한 |
| 프로젝트·SSE | 기존 저장 형식과 백업, polling 및 연결 복원, git·PR·활동 업데이트 |
| 계정·외부 연동 | 암호화 키와 credential 형식, MCP/agent/workflow/Telegram/approval 연동, 비밀값 비노출 |
| 재시작·Tauri | session-state 읽기/쓰기, 기존 프로세스 인계, Node 실행기 교체, Windows/WSL 검증 |

각 영역은 기존 서버와 같은 요청·실패·재접속 시나리오로 검증해야 합니다. 터미널 생성/입력/종료 및 감독 tick처럼 부작용이 있는 동작은 독립 tmux socket과 가짜 작업자를 사용해야 합니다. 실제 작업자에게 검증 명령을 주입하지 않습니다.

보드 이전 시 `scripts/cockpit-board.mjs`의 파일 직접 쓰기 fallback도 고려해야 합니다. `lib/board-service.js`의 `<file>.lock/owner-<pid>-<uuid>` 잠금 규약과 잠금 취득 후 재읽기, `review == supervisors[0]`, 콘텐츠 revision과 감독 메타데이터 갱신의 구별, `js/board-merge.js`의 3-way merge가 보존 조건입니다. 부분 normalizer로 감독·작업자 token·resume 시각·evidenceKeys·질문 수신자를 삭제하면 안 됩니다. 세션당 50개 제한은 오래된 완료 항목부터 적용하며 미완료 작업을 삭제하지 않습니다. 이 저장 계약과 별도로 독립 작업자 dispatch·감독 보고·대화 보호·기한·복구 경로를 함께 이전해야 합니다.

운영 데이터의 쓰기 주체는 한 서버만 허용합니다. 현재 개발 호스트의 운영 서버는 Rust로 전환되어 있습니다. 다른 설치를 전환할 때는 쓰기를 멈추고 저장 상태를 확정한 뒤 Rust로 인계해야 합니다. Node와 Rust가 운영 보드·session-state를 동시에 쓰는 방식은 지원하지 않습니다. 기존 파일 형식과 tmux 세션을 보존한 채 기존 실행기로 되돌릴 수 있다는 검증도 완료 조건입니다.

운영에 적용한 빌드와 보존 검증은 위 전환 기록으로 확인합니다. 로컬에서 새로 빌드한 파일이 운영에 자동 반영되지는 않습니다. preview 종료는 별도 저장소에만 영향을 줍니다. `--data-dir` 모드는 기존 파일에 쓰므로 preview와 같은 격리 실행으로 취급하면 안 됩니다. 운영 성능 및 메모리 개선 폭은 같은 부하와 실행 시간을 기준으로 측정해야 합니다.

## Linux 데스크톱 설치 파일

Linux x64에서는 `npm run build`가 기존 화면을 빌드하고 Rust 서버를 포함한 `.deb`를 생성합니다. 결과는 `src-tauri/target/release/bundle/deb/`에 저장합니다. GTK 3, WebKitGTK 4.1 및 Ayatana AppIndicator 개발 패키지가 빌드에 필요합니다. 설치 파일은 tmux, git, Node.js 18 이상과 데스크톱 런타임 의존성을 선언합니다. Node.js는 `cockpit-session`, `cockpit-board`, `cockpit-history` 보조 명령 실행에 사용하며 Node 서버나 `node_modules`는 설치 파일에 포함하지 않습니다.

앱은 지정 포트의 Rust 서버를 확인한 뒤 화면을 연결합니다. 이미 실행 중인 Rust 서버는 재사용합니다. 앱이 직접 시작한 서버에만 정상 종료를 요청하며 다른 포트 점유 프로세스는 종료하지 않습니다. 새 데스크톱 저장소의 노트와 로그 등은 사용자 데이터 폴더의 `desktop-state`에 저장하므로 읽기 전용 설치 경로에서 실행할 수 있습니다. 기존 설치 루트의 노트·로그를 이 경로로 자동 이전하지는 않습니다.

`python3 scripts/verify-native-installer.py --xvfb /usr/bin/Xvfb --node "$(command -v node)"`는 추출한 설치 파일을 별도 HOME·포트·Xvfb 화면에서 실행합니다. CLI, 두 창의 서버 공유, 재시작 후 데이터 보존 및 패키지 파일 불변성을 검사합니다. 결과와 화면 캡처는 `docs/_local/native-installer-verification.json`, `docs/_local/native-installer-desktop.png`에 기록합니다. 실제 시스템 설치와 트레이 종료 클릭은 이 검사 범위에 포함하지 않습니다.

## Windows 데스크톱과 WSL

Windows 실행기는 Ubuntu WSL에 설치된 `cockpit-prod.service`로 직접 연결합니다. WSL에 Cockpit 서버와 사용자 서비스가 미리 설치되어 있어야 하며, 이 설치 파일은 Windows 단독 서버나 WSL 자체를 설치하지 않습니다. 다른 배포판을 사용하면 `COCKPIT_WSL_DISTRO`로 이름을 지정합니다. 해당 배포판의 기본 사용자가 서비스를 소유해야 합니다.

앱은 서비스 시작 요청과 저장 토큰 조회를 최대 30초 동안 기다립니다. 이어서 최대 15초 동안 Rust 서버의 인증 응답을 확인합니다. 실패하면 연결 화면에 오류를 표시합니다. 이미 실행 중인 서비스는 재시작하지 않으며 앱의 트레이 종료도 공유 WSL 서버와 작업 세션을 종료하지 않습니다. Windows 앱은 별도 Node 프로세스나 로컬 중계 서버를 시작하지 않습니다.

Windows의 `npm run build`는 기존 설치 식별자를 유지한 NSIS 설치 파일을 생성합니다. Node 서버·`node_modules`·사용자 workflow를 설치 리소스에서 제외하며, 저장소의 Tauri 설정을 직접 덮어쓰지 않습니다. 사용자 데이터 초기화와 임의의 3847 포트 점유 프로세스 종료 훅도 제거했습니다. Tauri 기본 설치기의 앱 종료 확인은 유지합니다. 로컬 빌드 성공은 설치된 앱의 교체를 뜻하지 않으며 설치 적용은 별도로 검증해야 합니다. macOS는 아직 기존 Node 실행 경로를 사용합니다.

2026-10-10에 현재 Windows 호스트의 실행 파일을 백업 후 교체했습니다. 설치된 앱의 화면 로딩과 기존 WSL 서비스 PID 유지를 확인했으며, 적용 기록은 `docs/_local/windows-native-update.json`에 있습니다. 임시 앱 실행에서는 별도 Node 프로세스가 생성되지 않고 앱 종료 후에도 WSL 서비스가 유지됨을 확인했습니다. NSIS 설치기를 통한 전체 업그레이드와 실제 트레이 종료 클릭은 검증하지 않았습니다.
